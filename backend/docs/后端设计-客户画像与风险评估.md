# 客户画像与风险评估模块后端设计 V1

## 1. 模块范围

本模块只完成以下必要功能：

1. 查询客户列表；
2. 新建客户基础信息；
3. 查看客户基础信息、风险等级、资产画像和行为画像；
4. 基于结构化画像生成 AI 总结。

数据只来自四张表：`t_customer`、`t_product`、`t_holding`、`t_event`。

已有客户直接展示数据集提供的 `risk_appetite`。新建客户不要求前端填写风险等级，由后端通过简易风险规则生成演示用风险等级。

> 限制说明：现有数据中的年龄、收入、职业等字段与 R1-R5 的统计关联较弱，而且缺少正式风险测评问卷。因此该规则仅用于比赛 Demo 的新建客户流程，不应描述为银行正式适当性测评。

## 2. 简化架构

```text
前端页面
   ↓ HTTP/JSON
后端 API
   ├── CustomerService：客户新增与详情
   ├── ProfileService：资产、行为和标签聚合
   ├── RiskRuleService：新建客户风险规则
   └── AISummaryService：AI 画像总结
   ↓
MySQL 8.0（四张表）
```

技术栈采用 Python 3.12、Flask、PyMySQL 和 MySQL 8.0。V1 直接编写参数化 SQL，不引入 ORM、Redis、消息队列、数据仓库和独立画像表。

## 3. 数据职责

| 表 | 职责 |
|---|---|
| `t_customer` | 客户基础信息、当前风险等级、AI 总结缓存 |
| `t_product` | 产品名称、类型、风险、收益、波动和流动性 |
| `t_holding` | 客户与产品的持仓关系及金额 |
| `t_event` | 客户登录、咨询和投诉行为 |

详细画像不单独落表，由后端查询时动态聚合。AI 总结可以缓存到 `t_customer.ai_summary`，避免每次查看都调用模型。

## 4. 接口设计

统一返回格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

业务错误使用明确的 HTTP 状态码：参数错误 `400`、客户不存在 `404`、客户 ID 冲突 `409`、AI 服务异常 `502`。

### 4.1 客户列表

```http
GET /api/v1/customers?page=1&page_size=20&keyword=&risk_appetite=&vip_level=&city=
```

用途：客户画像首页的搜索、筛选和分页。

列表项返回：

```json
{
  "customer_id": "C000001",
  "age_group": "45-54",
  "city": "南京",
  "occupation": "企业职员",
  "aum": 96618.43,
  "risk_appetite": "R1",
  "risk_label": "谨慎型",
  "vip_level": "银卡",
  "has_app": false
}
```

### 4.2 新建客户

```http
POST /api/v1/customers
Content-Type: application/json
```

请求只包含基础信息，不接收 `customer_id`、`risk_appetite` 和 AI 总结字段：

```json
{
  "age_group": "35-44",
  "city": "上海",
  "occupation": "企业职员",
  "income_level": "30-50万",
  "register_date": "2026-08-26",
  "aum": 650000.00,
  "vip_level": "金卡",
  "has_app": true
}
```

后端处理步骤：

1. 校验枚举值、日期和非负金额；
2. 生成唯一 `customer_id`；
3. 在后端内部计算风险分数，并映射为 `risk_appetite`；
4. 只将最终的 `risk_appetite` 写入 `t_customer`；
5. 返回完整客户信息及风险计算摘要。

建议新建 ID 使用 `C` + 14 位时间 + 5 位随机数，例如 `C2026082615301284721`，并依赖数据库主键处理极低概率冲突；冲突时后端重新生成。不要通过查询 `MAX(customer_id)` 加一，以免并发重复。

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "customer_id": "C2026082615301284721",
    "age_group": "35-44",
    "city": "上海",
    "occupation": "企业职员",
    "income_level": "30-50万",
    "register_date": "2026-08-26",
    "aum": 650000.00,
    "risk_appetite": "R4",
    "risk_label": "成长型",
    "vip_level": "金卡",
    "has_app": true
  }
}
```

### 4.3 客户详情与画像

```http
GET /api/v1/customers/{customer_id}/profile
```

一次返回四部分：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "basic_info": {},
    "asset_profile": {},
    "behavior_profile": {},
    "ai_summary": null
  }
}
```

`basic_info` 直接来自 `t_customer`，包括风险等级及中文说明。

`asset_profile` 通过 `t_holding JOIN t_product` 动态计算：

- 客户 AUM；
- 当前产品持仓总金额；
- 持仓产品数量；
- 按产品类型的金额与占比；
- 按产品风险等级的金额与占比；
- 高流动性产品占比；
- 按金额加权的预期收益率；
- 持仓明细列表。

`behavior_profile` 通过 `t_event` 动态计算：

- 登录、咨询、投诉的累计次数；
- 近 30 天各类行为次数；
- 最近一次行为类型和日期；
- 动态展示标签。

注意：`t_customer.aum` 是客户资产管理规模，`SUM(t_holding.amount)` 是数据中可识别的产品持仓，两者可能不相等，接口分别返回。

### 4.4 生成 AI 画像总结

```http
POST /api/v1/customers/{customer_id}/ai-summary
```

后端先调用与详情接口相同的画像聚合逻辑，再将精简后的结构化数据发送给 AI。AI 不直接访问数据库，也不负责计算金额、比例或风险等级。

AI 输出要求：

- 160～240 个中文字符，使用“画像概述、需求洞察、服务建议”结构；
- 不逐项复述客户字段，最多引用 3 个关键数字；
- 将风险偏好、资产配置、流动性和近期行为综合为客户的复合需求，不做矛盾或异常判断；
- 将输入视为当前有效事实，不质疑产品等级、收益参数或数据录入；
- 给出 1～2 项客户经理可执行的需求了解、沟通或持续服务动作，但不推荐具体产品；
- 不承诺收益，不生成投资指令；
- 如果数据不足，只说明可以进一步了解需求，不评价数据质量。

DeepSeek 使用 JSON Output，返回 `overview`、`insight`、`suggestion` 和 `highlights`。后端校验三个正文段落，并只保留真实出现在正文中、长度不超过 12 个字符的高亮短语；最终 JSON 序列化后缓存到 `t_customer.ai_summary`。历史纯文本缓存会自动兼容为画像概述。

生成成功后更新：

- `t_customer.ai_summary`；
- `t_customer.ai_summary_generated_at`。

AI 调用失败不影响客户详情查询，接口返回 `502`，前端保留原有结构化画像。

## 5. 新建客户简易风险规则

### 5.1 规则目的

规则只处理新建客户，保证页面的新建流程可以自动得到一个可解释的 R1-R5 值。导入客户不重新计算，继续使用 CSV 原值。

### 5.2 计分方式

基础分为 50 分，然后按下表加减：

| 属性 | 取值 | 分值 |
|---|---|---:|
| 年龄段 | 18-24 | +8 |
|  | 25-34 | +10 |
|  | 35-44 | +6 |
|  | 45-54 | 0 |
|  | 55-64 | -8 |
|  | 65+ | -15 |
| 收入 | 10万以下 | -10 |
|  | 10-30万 | 0 |
|  | 30-50万 | +8 |
|  | 50万以上 | +15 |
| AUM | 小于10万元 | -8 |
|  | 10万（含）至50万元 | 0 |
|  | 50万（含）至100万元 | +5 |
|  | 100万元及以上 | +10 |
| 职业 | 退休 | -8 |
|  | 个体经营 | +5 |
|  | 专业技术 | +3 |
|  | 企业职员/公务员/其他 | 0 |

最终分数限制在 0～100，并映射为：

| 分数 | 风险等级 | 展示名称 |
|---|---|---|
| 0～25 | R1 | 谨慎型 |
| 26～40 | R2 | 稳健型 |
| 41～60 | R3 | 平衡型 |
| 61～75 | R4 | 成长型 |
| 76～100 | R5 | 进取型 |

`city`、`vip_level` 和 `has_app` 继续保存和展示，但 V1 不参与评分，避免把地区、渠道使用习惯或银行等级直接解释为风险偏好。

### 5.3 伪代码

```python
def assess_new_customer(payload) -> str:
    score = 50
    score += AGE_SCORE[payload.age_group]
    score += INCOME_SCORE[payload.income_level]
    score += AUM_SCORE(payload.aum)
    score += OCCUPATION_SCORE[payload.occupation]
    score = max(0, min(100, score))
    return map_score_to_risk_level(score)
```

风险计算与客户写入应处于同一个数据库事务中，不能出现客户已经创建但风险字段为空的情况。

## 6. 输入校验

| 字段 | 校验规则 |
|---|---|
| `age_group` | `18-24`、`25-34`、`35-44`、`45-54`、`55-64`、`65+` |
| `occupation` | `专业技术`、`个体经营`、`企业职员`、`公务员`、`其他`、`退休` |
| `income_level` | `10万以下`、`10-30万`、`30-50万`、`50万以上` |
| `register_date` | 合法日期，不晚于服务器当前日期 |
| `aum` | 大于或等于 0，最多两位小数 |
| `vip_level` | `普通`、`银卡`、`金卡`、`钻石` |
| `has_app` | 布尔值 |

## 7. 画像查询口径

资产聚合 SQL 需要避免一位客户多条持仓造成客户基础信息重复。建议分别查询客户基础信息、资产聚合、产品类型分布和行为聚合，再由 Service 组装返回；本阶段不必为了“一条 SQL”编写复杂联表。

常用口径：

```text
产品持仓总金额 = SUM(t_holding.amount)
产品类型占比 = 某类型持仓金额 / 产品持仓总金额
高流动性占比 = liquidity IN ('T+0','T+1') 的持仓金额 / 产品持仓总金额
加权预期收益率 = SUM(amount × expected_return) / SUM(amount)
近30天事件 = event_date >= CURRENT_DATE - INTERVAL 30 DAY
```

当分母为 0 时，占比和加权收益率返回 `null`，不要返回无穷值或伪造为 0%。

## 8. V1 明确不做

- 不做已有客户的风险偏好重算；
- 不做风险问卷、人工复核和风险评估历史版本；
- 不新增独立画像表；
- 不保存画像中间指标；
- 不实现产品、持仓和事件的新建接口；
- 不实现登录、权限、审计、消息队列和缓存服务；
- 不让 AI 决定风险等级或计算资产指标。

以上能力后续确有页面或算法需求时再增加。
