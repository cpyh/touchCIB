## 0. 这份文档解决什么

官方骨架（`src/docs/index.html`）定义了四 Tab 平台，其中 Tab3 要求「支持策略下钻与**执行追踪**」。围绕"执行追踪"展开讨论后，形成了三个递进的设计故事：**触达事件化 → 响应归因 → KPI 目标管理**，以及 2 天 demo 的范围建议。本文档即讨论产出，供小组评审。

## 1. 核心故事线（30 秒版）

**主线 = 数据闭环：数据如何变成运营动作，运营动作如何回到数据。**

```
数仓进数 → 离线加工(质量门禁) → 模型与规则(A1/A2/B) → 策略与触达(sent 事件)
   ↑                                                          ↓
   └─────────── 指标看板(KPI/漏斗) ← 事件回流(归因 responded) ←┘
```

- 环一 数仓与离线 pipeline：14 张分层表 + 批次溯源 + 41 项质量门禁 + **run_all 一键复现**
- 环二 算法层：A1 模型 / A2 规则引擎 / Part B 优化器（各有数字锚点）
- 环三 运营闭环：触达事件化 → 响应归因 → KPI 目标管理（本稿新增设计）
- 环四 四 Tab 平台：官方功能底线 → 验收载体（个性化/合规性/联动）

一句话答辩叙事：**"营销运营平台本质是银行版的投放系统——渠道选择靠规则引擎，活动目标对齐 HitRate 口径，效果归因走事件流，KPI 复盘分经理/渠道/活动三个管理视角。"**

与题目验收点的映射：

| 验收点 | 演示落点 |
|--------|---------|
| 个性化 | Tab3 策略卡 + A1 解释因子 |
| 合规性 | Tab3 规则轨迹（13 条规则命中/拦截） |
| 平台联动 | Tab2 改约束重算 + Tab3 调参重跑 + 埋点/归因/KPI 实时变化 |

## 2. 设计一：触达执行的事件化

### 2.1 建模依据

题目自身就是**双视角双事件表**：`t_event`（客户行为：login/consult/complaint）与 `t_campaign`（运营触达 + responded 标签）。平台新增的运营动作**跟随 `t_campaign` 的触达事实建模**，不混入客户视角的 `t_event`，官方表完全不动。

### 2.2 事件表（append-only，仅新增 1 张）

```
app_campaign_event
  campaign_event_id  PK
  strategy_id        关联策略（strategy_id = "{customer_id}:{rank}"，不建策略表）
  event_type         'sent' | 'responded'
  occurred_at        发生时间
  created_at         落库时间（审计）
```

### 2.3 状态推导（"未触达"零存储）

| 状态 | 推导规则 |
|------|---------|
| 待执行（未触达） | 策略存在，事件表中**无任何事件** |
| 已触达 | 有 `sent` 事件 |
| 已响应 | 有 `responded` 事件 |

事件表只记"发生了什么"，永不 UPDATE、永不 DELETE；漏斗 = 一次 `GROUP BY event_type`。

## 3. 设计二：响应归因

### 3.1 口径对齐题目

题目的 A2 判分即归因口径：**"下一周期实际购买产品 ∈ 客户 Top3 → 该客户命中"**。平台归因与之同构：

| 规则 | 逻辑 |
|------|------|
| 窗口 | `strategy_date ≤ buy_date ≤ strategy_date + 30 天`（窗口参数化，与评分口径同构） |
| 匹配 | 新增持仓产品 = 该客户 Top3 之一 → 归因到对应策略，写 responded 事件（含产品与金额） |
| 粒度 | 事件级：每个匹配购买各记一条；客户级：命中计 1 次（对齐 HitRate 口径） |

### 3.2 边界规则（答辩展示点）

| 情况 | 规则 |
|------|------|
| 窗口外购买 | 不归因 |
| 触达前已持有/购买 | 不算（as-of 排除） |
| 买 Top3 中 2 个产品 | 各记一条事件，客户级命中 = 1 |
| 同产品重复购买 | 只记首次 |
| 购买 Top3 之外产品 | 不归因（与题目口径一致） |

### 3.3 数据来源与诚实处理

- 生产路径：T+1 扫描 `t_holding` 增量 → 窗口匹配 → 自动追加 responded 事件；
- **演示现实**：策略日期 2026-04-15 之后的购买数据在评委手里（隐藏标签），拿不到 → demo 用**预置演示数据**（窗口内模拟持仓）展示归因链路，同时支持**手动埋点**（标记 responded 时过归因校验，现场可演示边界拒绝）。

## 4. 设计三：KPI 目标管理

### 4.1 三层架构（零新表，KPI 配置用内存/JSON）

```
事实层：app_campaign_event（归因后事件，append-only）
目标层：KPI 配置（指标、维度、目标值、周期）
展示层：完成率进度（实际 ÷ 目标，实时刷新）
```

### 4.2 三个管理视角（广告投放类比）

| 维度 | 投放系统对应 | 平台含义 | 示例 |
|------|------------|---------|------|
| 经理级（主角） | 销售团队业绩 | 客户经理 MGR001 | 4 月转化 ≥ 30 个 |
| 渠道级 | 媒体渠道效果 | sms/call/app_push/manager | manager 渠道响应率 ≥ 25% |
| 活动级 | 投放计划整体 | 本批 2000 客户活动 | 活动命中率 ≥ 55%（呼应 HitRate） |

### 4.3 演示口径（固定经理）

- `DEMO_MANAGER_ID = "MGR001"`，manager 渠道策略归 MGR001；事件表不加经理列；
- 答辩话术："demo 固定单经理；生产环境 manager_id 随触达记录写入事件表，KPI 聚合改为 GROUP BY manager_id 即可扩展。"
- 演示动作：标记 responded → 完成率 22/30 → 23/30，进度条 +1。

## 5. Demo 范围建议（2 天）

### 5.1 三档标准

| 档位 | 内容 | 效果 |
|------|------|------|
| 及格 | 四 Tab 静态数据展示 | "有看板"，只能看不能动 |
| **良好（目标）** | + 两条联动闭环 + KPI 实时变化 | 评委看到"改参数→结果变、点埋点→KPI 动" |
| 优秀（有余力） | + Tab1 进件落库全流程、规则开关面板 | 完整闭环 |

### 5.2 必须打磨的演示动作（4 + 1）

1. Tab2 改约束 → 秒级重算（API 已就绪）
2. Tab3 调 `w_cf`/manager 配额 → Top3 变化（引擎现成，包 generate 端点）
3. Tab3 标记已触达/已响应 → 状态流转（事件表 + 埋点 API）
4. Tab4 KPI 进度 +1、漏斗数字变化（dashboard 聚合）
5. **改源文件 → run_all 一键复跑 → 全链路产物更新 + 41 项质量门禁全绿**（工程分证据）

外加一个归因边界演示：预置"窗口外购买"数据 → 现场标记 responded 被拒 → 展示拒绝原因。

### 5.3 明确砍掉（2 天不碰）

- Tab1 完整进件落库（静态展示 + 口头讲流程）
- Kafka、多经理维度、declined 事件、鉴权审计
- 策略落库表（继续 CSV/内存 + 轨迹快照 JSON）
- **AI/LLM 接入（讲而不做**：话术模板可升级为 LLM 生成，规则引擎保证合规底线）

### 5.4 风险预案

演示翻车从来不是功能不够，而是交互挂了回不去：每个联动动作旁保留**静态回退**（如 generate 失败展示预生成对比）；服务一键启动脚本化；演示前完整走查 2 遍。
