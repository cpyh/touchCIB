> 分析基准日：**2026-03-31**；所有随机过程须固定 `random_state=42`。

> **关于 AI 辅助编码**：本次比赛允许使用 AI 辅助编码工具，但团队需理解、调试并能在答辩中解释所提交代码、模型、算法和系统设计。评委可要求现场修改、复跑或解释关键实现。

## 一、项目背景

随着零售银行财富管理业务向精细化、智能化转型，如何在海量客户、多元产品与多渠道触达之间实现精准匹配，已成为真实经营命题。本次考核围绕"智能财富管理运营平台"展开，涵盖**营销响应预测与策略生成**、**智能投顾组合配置优化**两条核心数据链路，并要求参赛团队完成支撑这两条链路的系统架构设计、规则/流程引擎实现，以及面向运营人员的可视化看板与平台演示。题目中的数据、约束与判分口径均来源于真实业务抽象，期望参赛者像银行产品技术团队一样，将模型、算法、工程三条线整合为可落地的完整方案。

## 四、Part A：营销响应预测与策略生成

### 4.1 A1 营销响应预测（30 分）

在 `t_campaign` 历史触达记录（含 `responded` 标签）上建立预测模型，对新触达名单 **`partA_test_contacts.csv`**（列：`contact_id, customer_id, product_id, channel, contact_date`，不含标签）中每条记录预测其认购概率。可结合 `t_customer`、`t_product`、`t_holding`、`t_event` 构造特征。

提交 **`partA_prediction.csv`**：

| 列名 | 说明 |
|------|------|
| `contact_id` | 测试触达记录唯一标识 |
| `response_prob` | 预测认购概率（∈ [0, 1]） |

须精确覆盖全部测试 `contact_id`，不得重复或多交；`response_prob` 不得为空、非数字或超出 [0, 1]；文件不得超过 5 MiB。违反任一要求时 **A1 记 0 分并送人工审核**，不影响格式正确的 A2。

后台使用隐藏真实标签计算三项指标，**均线性插值，无档位断崖**：

| 指标 | 满分 | 地板分 | 低锚点 → 分 | 高锚点 → 分 |
|------|------|--------|-------------|-------------|
| **AUC** | 17 分 | 3.4 分 | 0.79 → 6.8 分 | 0.85 → 17 分 |
| **F1** | 7 分 | 1.4 分 | 0.50 → 2.8 分 | 0.615 → 7 分 |
| **Lift@10%** | 6 分 | 1.2 分 | 2.6 → 2.4 分 | 3.3 → 6 分 |

- **F1**：后台自动扫描全部预测值（按 3 位小数去重）作为阈值候选，取最高 F1；
- **Lift@10%**：按 `response_prob` 降序取前 10%，用该组实际响应率除以全体响应率；
- 官方 LogisticRegression 基线 AUC 约 0.82；满分锚点可通过交互特征、持仓/行为特征与梯度提升类模型达到。

### 4.2 A2 营销策略生成

`partA_strategy_customers.csv` 给出 2000 位目标客户（列：`customer_id, strategy_date`）。请结合客户画像、历史持仓、行为事件、营销响应模型与产品属性，为每位客户生成 **Top 3 营销策略**，包含推荐产品、推荐渠道、营销时段建议与标准话术。

提交 **`partA_strategy.csv`**：

| 列名 | 说明 |
|------|------|
| `customer_id` | 目标客户 ID |
| `rank` | 推荐顺序，每位客户必须且只能为 1、2、3 |
| `product_id` | 推荐产品 ID，同一客户的 3 个产品不得重复 |
| `recommended_channel` | `sms` / `call` / `app_push` / `manager` |
| `recommended_time` | 规定营销时段枚举之一 |
| `marketing_script` | 10–300 个字符的营销话术 |

`recommended_time` 只允许：`工作日09:00-12:00`、`工作日12:00-14:00`、`工作日18:00-21:00`、`周末09:00-12:00`、`周末14:00-18:00`。须精确覆盖目标客户，每人恰好 3 行，文件不得超过 10 MiB；任一强制格式不符时 **A2 记 0 分**，不影响 A1。

后台为每位目标客户保留一个隐藏的下一周期实际购买产品。若该产品落在提交的 Top 3 中，该客户记为命中。

> **HitRate@3 = 命中客户数 ÷ 2000**

| 指标 | 满分 | 地板分 | 低锚点 → 分 | 高锚点 → 分 |
|------|------|--------|-------------|-------------|
| **HitRate@3** | 5 分 | 0 分 | 0.30 → 2 分 | 0.55 → 5 分 |

锚点之间线性插值，并夹在 [0, 5] 内。推荐渠道、时段与话术是必交的可执行策略字段，**不额外改变 HitRate@3 自动分**；其个性化、合规性与平台联动由 Part D 运营工作台现场验收。

### 4.3 共同时间与复现要求

> **时间穿越约束**：A1/A2 构造特征时不得使用对应 `contact_date` / `strategy_date` 之后的事件或持仓信息；答辩时需说明 as-of 截断方式。特征工程、模型对比与可解释分析须能现场复现。

## 五、Part B：投资组合配置优化

### 5.1 发放文件

- `t_product.csv`（30 个产品的 `expected_return`/`volatility`/`risk_level`/`liquidity` 等字段，同 3.2 节）；
- **`partB_scenarios.csv`**（20 个客户场景）：

  | 列名 | 说明 |
  |------|------|
  | `scenario_id` | 场景唯一标识 |
  | `total_amount` | 可配置总资金（元） |
  | `lambda` | 风险厌恶系数（效用函数参数） |
  | `max_single_weight` | 单产品权重上限 |
  | `max_high_risk_weight` | 高风险产品（R4/R5）权重合计上限 |
  | `min_liquid_weight` | 高流动性资产权重合计下限（含现金） |
  | `min_holdings` | 最低持仓产品数（`weight >= 1e-6` 的产品计入） |

- **`partB_corr_matrix.csv`**：30×30 产品相关系数矩阵（行列均为 `product_id`），用于计算组合波动率。

### 5.2 任务描述

为 `partB_scenarios.csv` 中每个场景给出产品配置权重，在满足全部约束的前提下，**最大化效用函数 U**。

**效用函数：**

$$U = \sum_i w_i \cdot r_i - \lambda \cdot \sqrt{w^\top \Sigma w}$$

其中：
- $w_i$ 为产品 $i$ 的配置权重；
- $r_i$ 为产品 $i$ 的 `expected_return`；
- $\lambda$ 为该场景的风险厌恶系数；
- $\Sigma_{ij} = \sigma_i \cdot \sigma_j \cdot \rho_{ij}$，$\sigma_i$ 为 `volatility`，$\rho_{ij}$ 来自 `partB_corr_matrix.csv`；
- 现金（余下仓位 $1 - \sum w_i$）的预期收益与波动率均为 0。

**约束（逐条校验；任一违反则该场景效用记 0）：**

1. 现金权重 $= 1 - \sum_i w_i \geq 0$，即产品权重之和 $\leq 1$；
2. 每个产品权重 `w_i` ∈ `[0, max_single_weight]`；
3. 高风险产品（`risk_level` ∈ {R4, R5}）权重合计 ≤ `max_high_risk_weight`；
4. 高流动性资产权重合计 + 现金权重 ≥ `min_liquid_weight`（高流动性：`liquidity` ∈ {T+0, T+1}，现金计入流动性）；
5. 持仓产品数 ≥ `min_holdings`，其中**持仓按 `weight >= 1e-6` 计入**（用极小权重凑数无效）。

**口径补充（重要）：**
- **浮点容差**：上述所有约束的自动校验容差为 **`1e-6`**（例如 $\sum w_i \leq 1 + 10^{-6}$ 视为满足）。
- **`total_amount` / `min_invest`**：自动评分**只按权重约束计算**，`total_amount`（场景总资金）与 `min_invest`（产品起投金额）**仅用于答辩展示，不参与自动评分**。
- **重复行**：同一 `scenario_id + product_id` **不得重复**，重复则该场景判 0。

### 5.3 提交文件

上传文件：**`partB_allocation.csv`**

| 列名 | 说明 |
|------|------|
| `scenario_id` | 对应场景标识 |
| `product_id` | 产品标识 |
| `weight` | 配置权重（≥ 0） |

**格式要求**：
- 每个场景只需列出 **weight > 0** 的产品行；
- 未出现的产品权重视为 0；
- 每行 `weight ≥ 0`，不得为空或非数字；
- `product_id` 须来自发放的产品池（P001～P030）；
- 出现空值/非数字权重或未知 `product_id` 的场景判 0；
- 同一 `scenario_id + product_id` **不得出现多行**，重复则该场景判 0。

### 5.4 判分规则

后台逐场景校验可行性（违反约束的场景效用记 0），汇总 20 个场景的效用 `U_total`，与预置锚点线性插值：

| 锚点 | 说明 | 对应得分 |
|------|------|----------|
| `baseline_U` | 官方等权可行解汇总效用 | 6 分 |
| `optimal_U` | 官方近优解汇总效用 | 15 分 |
| 地板 | — | 3 分 |

得分 = `max(3, min(15, 6 + (total_U − baseline_U) / (optimal_U − baseline_U) × 9))`

> 优化不要求全局精确最优，逼近近优解即可得满分。
