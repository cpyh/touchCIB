环二 · 算法层

模型与规则：三条算法线的数字锚点

A1 响应预测 ✅

AUC 0.8828 ｜ F1 0.6185 ｜ Lift 4.0047

46 特征 · as-of 三道防线 · 时间留出验证

局部解释 top±5 因子 → 个性化载体

A2 规则引擎 ✅

14 规则 · 两阶段流水线 · 24000 条策略

模型管产品、规则管其余；manager 配额 600

规则轨迹逐条可查 → 合规性载体

Part B 优化 ✅

gap ≈ 1e-18 ｜ total_U ≈ 0.6112

凸化 + 多起点 + KKT 精修 + 切平面上界证书

全局最优性证书 → 创新栏素材

A1 对全量客户产品组合预测响应概率；A2 不改写模型分数，只做基础规则过滤，并为每条 Top3 策略固化可追溯规则证据。
环三 · 运营闭环 1/3

触达执行的事件化

运营动作不是"改个状态字段"，而是一次埋点事件，append-only 落库。跟随题目自身 t_campaign（运营触达事件流）建模，官方表零改动。

事件表（仅新增 1 张）

字段说明
campaign_event_id主键
strategy_id关联策略（约定 {customer_id}:{rank}）
event_type'sent' ｜ 'responded'
occurred_at / created_at发生时间 / 落库时间

状态推导："未触达"零存储

策略已生成ADS 有完整 Top3
→
待执行无事件
→
已触达有 sent
→
已响应有 responded

永不 UPDATE、永不 DELETE；漏斗 = 一次 GROUP BY event_type。

环三 · 运营闭环 2/3

响应归因：间隔多天认购，算谁的？

题目 A2 判分本身就是归因口径："下一周期实际购买产品 ∈ 客户 Top3 → 该客户命中"。平台归因与之同构。
窗口strategy_date ≤ buy_date
≤ +30 天（可调参数）
→
匹配新购产品 ∈ Top3
→
写事件responded 挂对应策略

边界规则（现场演示"窗口外购买"被拒）

情况规则
窗口外购买不归因
触达前已持有/购买不算（as-of 排除）
买 Top3 中 2 个各记一条；客户级命中 = 1
同产品重复购买只记首次
买 Top3 之外不归因

诚实处理

生产：T+1 扫描 t_holding 增量自动归因；演示：2026-04-15 后购买数据在评委手里 → 预置数据展示链路 + 手动埋点（过归因校验）。

环四 · 四 Tab 平台

官方四 Tab：需求底线 → 验收载体

Tab官方功能要求（摘要）载体落点
Tab1 进件与风险评估录入基本信息，自动风险偏好评估，生成画像画像 API + 评估逻辑（可静态化）
Tab2 智能投顾推荐按风险偏好与场景参数调用 Part B，输出组合方案/portfolio/* API + gap 证书
Tab3 营销运营工作台A1 概率 + A2 Top3，策略下钻与执行追踪名单 + 策略卡 + 轨迹 + 埋点
Tab4 可视化看板模型效果、资产配置分布、营销转化漏斗dashboard 聚合 + 漏斗 + KPI

三个现场验收维度 → 载体

  • 个性化 → Tab3 策略卡 + A1 解释因子（top±5）
  • 合规性 → Tab3 规则轨迹（14 条规则命中/拦截）
  • 平台联动 → Tab2 改约束重算 + Tab3 调参重跑 + 埋点/KPI 实时变化

落地 1/2

2 天 Demo 范围

及格档

四 Tab 静态展示。
只能看不能动。

良好档 2 天目标

+ 数据闭环可演示：改参数→结果变；点埋点→KPI 动；一键复跑→门禁全绿。

优秀档

+ Tab1 进件落库全流程、规则开关面板。
有余力再做。

演示动作清单（4 + 1）

  • ① Tab2 改约束 → 秒级重算（API 已就绪）
  • ② Tab3 调整 manager 配额 → 推荐渠道变化（试算不覆盖 ADS）
  • ③ Tab3 标记已触达/已响应 → 状态流转（事件表 + 埋点 API）
  • ④ Tab4 KPI 进度 +1、漏斗数字变化（dashboard 聚合）
  • ⑤ 改源文件 → run_all 一键复跑 → 产物更新 + 41 项门禁全绿（工程分）

砍掉 2 天不碰

Kafka、多经理、declined、鉴权审计｜ AI/LLM 话术生成（作为展望）：规则引擎仍保留合规底线。

落地 2/2

两天排期与风险预案

时段Day 1（后端）Day 2（联调 + 打磨）
上午事件表 DDL + 归因模块 + 单元测试预置演示数据 + 前端联调
下午埋点 API + 状态查询 + generate + dashboard summary演示脚本走查 + 全量复跑
晚上run_all 编排 + 测试全绿 + 发 JSON 样例给前端失败预案 + 提交包确认

风险预案

演示翻车从来不是功能不够，而是交互挂了回不去：每个联动动作旁保留静态回退；服务一键启动脚本化；演示前完整走查 2 遍。

待小组讨论的 6 个问题

点击问题展开背景说明；点击左侧方框标记"已达成一致"。

1. 数据闭环作为主线叙事是否认可？每环数字锚点（41 全绿 / AUC 0.86 / gap≈0 / KPI 22→23）是否要调？
闭环主线同时服务讨论与答辩：队友对"我们在讲一个圈"有共识后，各自模块的定位自然清晰。
2. 事件化 + 归因方案是否认可？窗口 30 天固定还是现场可调？
窗口做成现场可调参数，评委问"窗口多长"可直接演示调整后归因结果变化——多一个演示点，成本约 10 行代码。
3. KPI 维度：固定经理 MGR001 + 渠道/活动陪衬，是否认可？
经理级是主角（演示动作 +1），渠道/活动级数据现成零造数，证明"目标管理是配置化的"。
4. run_all 一键复现（演示动作 ⑤）加入 2 天范围？预置演示数据谁准备谁验收？
run_all 约 150 行，Day 1 晚上完成。预置口径 = "截至 4 月中旬的执行进度"，后端生成、前端联调验收。
5. 前端分工：四 Tab + 5 个动作给前端；后端出 API 契约 JSON 样例？
后端 Day 1 晚上必须把接口的请求/响应 JSON 样例发给前端才能并行开工。骨架 index.html 在 src/docs/。
6. Tab1 的度：静态展示可以接受，进件表单延后？AI/LLM 维持"讲而不做"？
2 天档建议 Tab1 静态 + 口头讲流程；AI 不做实现，答辩留一句"话术模板可升级 LLM、规则引擎保合规底线"。
